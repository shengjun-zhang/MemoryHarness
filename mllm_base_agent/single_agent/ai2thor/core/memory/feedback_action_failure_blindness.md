# "幻觉式完成"：动作失败后未察觉，凭空断言成功 —— DONE 类失败的头号原因

**Observed:** 对 2026-07-28 的 single-agent AI2-THOR 全量 benchmark
（`doubao_ai2thor_k3_s0.5_w10_20260728_135530`，311 个任务，成功率 **0%**）
做失败归因分析：58% 的失败（180/311）是 `Model claimed DONE but success
conditions not met`；对其中随机抽查的 7 个具体案例逐帧复盘，**全部 7 个**
都遵循同一模式：某个关键交互动作（`PickupObject`/`PutObject`/
`ToggleObjectOn`/`OpenObject`）因为距离超出 1.0m 交互范围而在环境侧报错
失败（`error_message` 里明确写出了实际距离，通常 1.3m–3.3m），但模型在
**下一步**的 Observation Description 中完全无视这个报错，凭空描述出
"任务已完成"的画面（比如"咖啡机显示 READY 状态"、"水已经装满"、
"物品已经放到梳妆台上"），然后直接输出 `DONE`。

这是目前观测到的单体（single-agent）ai2thor 上**最大、最系统性**的失败
模式，且是纯粹的"反馈闭环缺失"问题——与空间导航能力、任务理解能力
无关，是可以通过更严格的自检习惯规避的。

## 典型案例（来自真实 episode 日志）

- `ai2thor05025`（"Fill mug & clean bed"）：`FillObjectWithLiquid` 因距离
  1.3m 报错失败，模型下一步描述"水已装满"，直接 DONE。
- `ai2thor04503`（"Pick up baseball bat"）：两次 `PickupObject` 分别因
  2.0m/1.7m 距离失败，模型仍描述"已捡起球棒"，DONE。
- `ai2thor05079`（"Turn on coffee machine"）：`ToggleObjectOn` 因 2.4m
  距离失败，模型描述"显示 READY"，直接 DONE。
- `ai2thor05039`（"Move keychain to dresser"）：`PickupObject`(2.2m) 和
  `PutObject`(3.3m) 均失败，模型从未真正靠近物体，却直接幻觉搬运已完成。

## 根本模式

1. 模型的"下一步观察描述"似乎更依赖**先验预期**（"我打算做的动作应该
   已经生效了"），而不是真正逐字核对上一步 `error_message` / 环境反馈。
2. 一旦某个交互连续失败 2 次以上，模型既不会明确诊断原因（例如"我距离
   还是太远"），也不会诚实地报告失败继续尝试或放弃，而是径直转向断言
   成功——这是一种比"过早放弃"更隐蔽也更致命的失败模式，因为它每次都
   会触发一次真实的、代价高昂的评测器拒绝（DONE 被拒绝的重试成本高于
   继续正常探索）。

## 强制自检规则（每次输出 DONE 前必须执行）

在输出 `DONE` 之前，必须在 `<THINK>` 中显式回答以下问题：

1. **重新读取你上一步动作的执行结果**：上一步的 `error_message` /
   反馈是否为空？如果上一步（或最近 2 步内）任何一次关键交互动作报错
   （包含 "not in view"、"distance"、"too far"、"failed" 等字样），
   那么该交互**没有生效**，无论你多么确信自己应该已经完成了它。
2. 把任务指令拆分成独立的子句/条件清单，逐条确认：**当前这一帧图像**
   里是否有直接视觉证据支持该条件成立（而不是"应该已经是这样了"）。
3. 特别警惕以下"编造成功"的高发场景：
   - 液体填充类（`FillObjectWithLiquid`、咖啡机加热）：除非清晰看到
     容器内有液体/颜色变化，否则不要假设已完成。
   - 拾取/放置类（`PickupObject`/`PutObject`）：确认手持状态或目标位置
     的物体确实可见，而不是"应该已经放好了"。
   - 开关类（`ToggleObjectOn`/`OpenObject`）：确认指示灯/开关的视觉
     状态变化，而不是回忆"我发出过这个指令"。
4. 如果上述任意一条无法给出"当前画面中的直接证据"，**不要**输出
   `DONE`——先重新靠近/重新执行该交互一次，确认这次没有报错，再考虑
   完成。

## 交互失败后的正确处理流程（而非视而不见）

1. 读取 `error_message` 中的具体距离数字。
2. 如果报错是距离相关（"distance: Xm"），先靠近到 1.0m 以内再重试，
   而不是假装它已经成功。
3. 如果同一个动作 + 同一个物体已经连续失败 2 次，**换一种诊断**：是不是
   物体类型名写错了？是不是应该先做前置动作（比如先 `PickupObject` 才能
   `PutObject`）？而不是第三次原样重复，也不是直接放弃转而幻觉成功。
4. 只有在这一步的反馈明确无报错、且画面证据支持时，才把这一步视为
   "已完成"，继续向后规划。

## 反模式（不要这样做）

- 不要把"我已经发出了正确的动作指令"等同于"世界状态已经改变"——环境
  可能因为距离/朝向/物体不可见等原因静默或显式地拒绝了这次交互。
- 不要在没有当前帧视觉证据的情况下，仅凭"计划应该已经执行完"就输出
  `DONE`。
- 不要把上一步的 `error_message` 留在上下文里却不引用它——每次考虑
  DONE 之前都应该显式回看最近几步是否有报错。
