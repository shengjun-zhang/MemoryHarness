# 动作字符串/解析错误——白白浪费一次完整的重试往返

这些是纯格式类错误：每一次解析失败都会消耗一次额外的 VLM 调用（运行时
最多重新提示 3 次才会放弃），是最容易被彻底根除的一类错误。

## 1. `ThrowObject` 不带物体参数

`ThrowObject` 扔出的是**当前手里已经拿着的物体**——它是一个无参动作，
不是带目标的动作。

- 正确：`<ACTION>ThrowObject</ACTION>`（不带括号，不带物体）。
- 错误：`ThrowObject(Bowl)`、`ThrowObject()`。
- 前置条件：手上必须已经拿着物体，否则这个动作没有意义。

## 2. 缺失 `<ACTION>` 标签

模型的原始回复完全省略了该标签（例如把动作写成纯文本、被 token
限制截断、或者用了不相关的格式包裹）。

- **始终**把选定的动作包裹在 `<ACTION>...</ACTION>` 里，即使是像
  `DONE`、`RotateRight` 这样最简单的动作。
- 保持 `<THINK>` 简洁——过长的思考块会增加在真正输出 `<ACTION>` 标签
  之前触及 token 限制的风险。优先保证 `<ACTION>` 标签被完整输出，而
  不是追求一段详尽无遗的思考过程。
- 不要嵌套标签，也不要在标签外面套 markdown 代码块——按照系统提示词
  展示的格式原样输出纯文本标签。

## 3. 物体类型名大小写/拼写错误

动作解析器要求**精确的 PascalCase** 物体类型名，与系统提示词的可交互
物体目录完全一致（例如 `HousePlant`，而不是 `houseplant` 或
`Houseplant`）。拼写或大小写错误会导致"物体在场景中不存在"这类报错，
即使正确的物体明明可见——参见
`feedback_task_semantics_pitfalls.md` 中"物体类型名用错且屡次报错也不
自我纠正"的真实案例：连续 3 次报错却始终没有意识到是名字写错了。当同一
个动作反复报错"does not exist"时，第一时间应该怀疑拼写问题，回头对照
系统提示词的目录核对准确名称，而不是假设是距离/朝向问题反复重试同一个
错误名字。

## 4. 步幅/角度粒度后缀

移动动作可以带一个粒度后缀：`MoveAhead(Small)`、`MoveAhead(Medium)`、
`MoveAhead(Large)`（Small=0.25m，Medium=0.5m，Large=1m）。不要直接传
数值距离（例如 `MoveAhead(0.5)`）——使用命名的粒度关键字，或者用不带
参数的裸动作走环境默认步长。

## 总则

当一个动作解析失败时，不要重新发送一个几乎相同的畸形字符串期望它能
工作——重新仔细阅读系统提示词里 `**Action Format Notes**` /
`**Output Format**` 部分给出的精确动作语法，产出语法完全匹配的字符串
之后再重试。
