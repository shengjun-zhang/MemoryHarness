# DONE 被拒绝：输出 DONE 之前的强制自检清单

**Observed:** `DONE` 不是自我报告，它会触发真实的终态评测器对**实际**
AI2-THOR 物体图谱的检查，而不是你对世界状态的信念。2026-07-28
single-agent benchmark 中，58%（180/311）的失败都是
`Model claimed DONE but success conditions not met`——这是目前观测到的
最大失败类别。深入分析显示，其中绝大多数案例的根因是"上一步交互动作
已经报错失败，但模型下一步凭空断言成功"（完整分析见
`feedback_action_failure_blindness.md`，那里是本文件的必读前置内容）。
本文件聚焦于更通用的 DONE 自检规范。

## DONE 被拒绝的常见原因

1. **动作失败但未被察觉**（本 benchmark 里最主要的原因，见
   `feedback_action_failure_blindness.md`）：上一步的交互因为距离/朝向
   等原因报错，但没有真正改变世界状态。
2. **部分子目标完成**：多物体/多状态的任务（如"把两个鸡蛋放进平底锅"、
   "打开冰箱**并且**关灯"）是按合取（AND）来判定的——完成 90% 仍然是
   失败。要重新数一遍指令里的每一个分句，而不是只关注你主观上花了
   最多精力的那一部分。
3. **状态漂移**：更早被你自己改变的物体状态（打开、切换开关、拾取），
   可能被后续动作意外撤销（比如为了绕路碰撞/推动了某个物体）——要验证
   **当前这一帧**的状态，而不是几步之前的记忆。
4. **多实例歧义**：场景里如果有多个同类型物体（两个 `CounterTop`、
   两个 `Chair`），交互会默认作用于**最近的可见实例**——确认你眼前
   看到的状态确实符合任务的隐含目标，而不是"某个同类型的物体存在
   即可"。
5. **任务隐含前置条件未满足**：详见 `feedback_task_semantics_pitfalls.md`
   （例如任务要求"clean mug"但你从未执行过 `CleanObject`）。

## 输出 DONE 之前的强制检查清单

在 `<THINK>` 中显式过一遍以下问题：

1. 把任务指令拆成独立的子句/子目标列表。
2. 对每一条子句，**当前这一帧图像**里是否有直接视觉证据它已经满足？
3. 你最近 1-2 步的动作是否有任何报错？如果有，那部分子目标大概率还
   没有真正完成，无论你的意图是什么。
4. 有没有可能某个更晚的动作（包括为了导航而做的碰撞/推动）撤销了更早
   完成的子目标？
5. 如果以上任意一条回答是"不确定"或"否"，**不要**输出 DONE——先做
   一次验证性动作（移动/旋转查看，或重新执行失败的交互）再考虑完成。

## DONE 被拒绝之后

如果你的 `DONE` 被拒绝：不要不做任何改变就立刻再次输出 `DONE`。先找出
具体是哪个子句仍未满足（重新靠近查看，或重新执行报错的交互），修复或
重新验证它，然后再重试 `DONE`。如果你确信所有条件都已满足但评测器不
认可，优先怀疑多实例歧义（上面第 4 条）——你交互的可能不是任务隐含
指向的那个具体实例。
